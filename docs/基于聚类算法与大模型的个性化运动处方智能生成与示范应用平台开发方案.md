# 基于聚类算法与大模型的个性化运动处方智能生成与示范应用平台开发方案

## 一、项目概述

本项目拟建设一套面向社区居民、慢病风险人群、高校师生、老年人群及企事业单位职工的 **AI 个性化运动处方智能生成与健康干预服务平台**。平台以六类运动健康数据为基础，以风险分级、聚类分型、规则引擎、RAG 知识库、大模型生成和专家审核为核心技术路径，形成从健康数据采集、风险筛查、智能分型、处方生成、专家审核、运动执行、反馈优化到阶段评估的完整闭环。

项目建设目标不是开发一个简单的 AI 问答工具或演示系统，而是建设一套可真实上线、可持续运营、可专家审核、可科研沉淀、可示范推广的产品级系统。总体建设方案中已明确，本平台的核心在于建立“数据采集—风险筛查—智能分型—处方生成—专家审核—运动执行—反馈优化—效果评估”的闭环体系。

------

## 二、建设背景与必要性

当前运动健康服务存在四类突出问题：

第一，数据分散。体质测试、身体成分、生化指标、疾病风险和运动反馈往往分布在不同系统、纸质表格或设备报告中，难以形成统一健康画像。

第二，处方效率不足。传统运动处方高度依赖专家经验，大规模服务社区居民、慢病风险人群和高校师生时，专家服务能力有限，难以高效覆盖。

第三，安全边界不足。普通健身建议容易忽视高血压、糖尿病、关节疼痛、用药影响、胸痛、晕厥等风险因素，存在不适宜运动推荐的风险。

第四，反馈闭环缺失。多数运动建议只停留在一次性出方，缺少运动执行打卡、RPE、心率、不适反应、复测结果和处方动态调整。

因此，本项目拟通过 AI 技术和运动健康专业规则结合，建设一个以“规则先行、专家把关、闭环迭代、科研沉淀”为核心特征的平台。总体方案也明确提出，平台应兼顾科技攻关、应用示范、成果转化和公共服务属性。

------

## 三、项目建设目标

### 3.1 总体目标

建设一套集 **多源数据采集、健康风险筛查、人群聚类分型、大模型运动处方生成、规则安全校验、专家审核发布、运动执行反馈、动态优化调整和效果评价** 于一体的 AI 运动处方智能服务平台，形成科学、安全、可解释、可追溯、可推广的运动处方生产与应用体系。

### 3.2 分项目标

| 目标类别 | 建设目标                                       | 主要成果                               |
| -------- | ---------------------------------------------- | -------------------------------------- |
| 数据目标 | 建立六类运动健康数据采集标准和用户健康画像模型 | 数据字典、数据库结构、健康画像报告     |
| 算法目标 | 构建规则分型 + 聚类算法相结合的人群分型模型    | 分型标签体系、聚类模型、算法评估报告   |
| 生成目标 | 建立规则约束 + RAG 知识增强 + 大模型生成流程   | 处方生成引擎、提示词模板、处方报告模板 |

| 应用目标 | 支持社区、高校、慢病干预和体育场馆等场景试点   | 服务记录、处方数量、用户反馈、复测数据 |
| 成果目标 | 沉淀软件、数据、标准、论文、专利和示范材料     | 软著、标准规范、示范报告、科研数据集   |

## 四、建设原则

本项目开发遵循以下原则：

1. **安全优先**：运动处方生成必须以风险筛查和禁忌识别为前置条件。
2. **规则先行**：大模型不能自由生成运动建议，必须受数据标准、知识库、模板库和规则库约束。
3. **专家把关**：中高风险人群必须进入专家审核流程，AI 只能生成初稿。
4. **闭环迭代**：处方不是一次性结果，应根据用户反馈和复测数据动态调整。
5. **产品化上线**：系统需具备真实数据录入、真实处方生成、真实专家审核、真实用户执行反馈能力，不做静态 demo。
6. **科研沉淀**：系统在服务过程中沉淀脱敏数据，支撑后续课题、论文、标准和成果转化。

## 五、平台总体定位

平台定位为：

> **AI 运动处方智能生成与健康干预服务中台**

平台面向四类核心用户：

| 用户角色 | 使用目标                                                     |
| -------- | ------------------------------------------------------------ |
| 普通用户 | 建立健康档案、完成风险筛查、查看运动处方、执行打卡、获得阶段反馈 |
| 专家人员 | 审核 AI 处方初稿、修改处方、发布处方、跟踪用户执行情况       |
| 管理人员 | 管理用户、专家、规则库、模板库、知识库、试点数据和运营统计   |
| 科研人员 | 查看脱敏数据、开展分型分析、干预效果分析和科研导出           |

平台应用边界必须明确：系统提供运动健康指导、风险提示、运动处方建议和运动干预跟踪服务，不替代医疗诊断、药物治疗和临床处置。对于胸痛、晕厥、严重气短、血压显著异常、急性损伤、医生明确限制运动等用户，平台不直接出具训练处方，而是进入医学评估或专业转介流程。

## 六、总体技术路线

平台采用：

> **六类数据采集 + 规则引擎 + 聚类算法 + RAG 知识库 + 大模型生成 + 专家审核 + 反馈闭环**

总体技术路线如下：

```text
用户建档
  ↓
六类数据采集
  ↓
风险规则引擎判定 R0 / R1 / R2 / R3
  ↓
规则分型 + 聚类算法生成健康画像
  ↓
匹配处方模板与运动项目库
  ↓
RAG 检索专业知识库
  ↓
大模型生成 FITT-VP 运动处方初稿
  ↓
规则二次安全校验
  ↓
R0 / R1 自动发布或抽查
R2 专家审核后发布
R3 不生成训练处方，仅提示评估或转介
  ↓
用户执行与运动反馈
  ↓
2—4 周小调整，8—12 周阶段评估
  ↓
生成新版本处方与效果评价报告
```

总体方案建议采用“数据层—算法层—知识层—规则层—生成层—审核层—应用层”的七层架构，并明确“规则引擎 + RAG 知识库 + 大模型 + 专家审核”的组合方式：规则引擎负责安全边界，RAG 知识库负责专业依据，大模型负责综合生成和个性化表达，专家审核负责中高风险人群把关。

2. 知情同意确认。
3. 基础健康档案填写。
4. 体质测试数据录入。

6. 生化指标录入或暂缺。
7. 疾病与运动风险问卷。
8. 风险等级查看。

11. 运动打卡。

用户端重点不是展示复杂算法，而是让用户清楚知道：

```text
我能不能开始运动；

什么时候需要停止；
什么时候需要复测。
```

## 八、核心功能模块设计

### 8.1 六类数据采集模块

平台以六类数据为基础：

1. 基础信息数据。
2. 体质测试数据。
3. 身体成分数据。
4. 生化与健康指标数据。
5. 疾病与运动风险数据。
6. 运动过程与反馈数据。

六类数据标准文件明确说明，这些字段可作为数据库建表、用户采集表单、专家审核页面和运动处方生成模型输入的基础依据。

第一版建议必采字段如下：

| 数据类别 | 第一版必采字段                                               |
| -------- | ------------------------------------------------------------ |
| 基础信息 | 年龄、性别、身高、体重、BMI、腰围、运动目标、运动习惯        |
| 体质测试 | 静息心率、血压、肺活量、握力、坐位体前屈、闭眼单脚站立、疼痛评分 |
| 身体成分 | 体脂率、骨骼肌量、内脏脂肪等级、基础代谢率                   |
| 生化指标 | 空腹血糖、血脂四项；没有体检数据时可暂缺                     |
| 风险筛查 | 高血压、糖尿病、冠心病、关节疼痛、胸痛、头晕、气短、用药情况 |
| 运动反馈 | 运动项目、时长、频率、平均心率、RPE、完成度、不适反应        |

------

### 8.2 风险分级与规则引擎模块

平台设置四级风险：

| 风险等级 | 类型         | 系统动作                                 |
| -------- | ------------ | ---------------------------------------- |
| R0       | 普通健康型   | 自动生成基础处方，可直接发布             |
| R1       | 低风险改善型 | 自动生成改善型处方，可发布，建议抽查     |
| R2       | 中风险干预型 | 生成谨慎型处方初稿，必须专家审核后发布   |
| R3       | 高风险转介型 | 不生成训练处方，只输出安全提醒和评估建议 |

规则引擎负责：

1. 红色风险识别。
2. 黄色风险识别。
3. 强度上限控制。
4. 动作禁忌控制。
5. 审核触发控制。
6. 运动过程预警。
7. 动态调整判断。

关键原则是：

```text
R3 永远不生成训练计划；
R2 永远不允许 AI 直接发布；
大模型输出必须经过规则二次校验；
专家修改、发布和驳回必须留痕。
```

------

### 8.3 人群分型与聚类算法模块

第一阶段采用“专家规则分型 + 聚类验证”的方式。

初始分型包括：

1. 肥胖代谢风险型。
2. 心肺功能不足型。
3. 肌力不足型。
4. 柔韧平衡不足型。
5. 慢病稳定干预型。
6. 损伤风险限制型。
7. 久坐低体能型。
8. 老年功能下降型。

第二阶段在样本量积累后，引入 K-means、DBSCAN、层次聚类、高斯混合模型等方法，对用户群体进行聚类建模和专家校准。

聚类结果只用于健康画像和处方模板匹配，不能覆盖风险规则。安全规则优先级永远高于算法分型结果。

------

### 8.4 RAG 知识库模块

知识库建设内容包括：

1. 运动项目库。
2. FITT-VP 处方原则库。
3. 慢病运动干预知识库。
4. 禁忌症知识库。
5. 传统运动知识库。
6. 专家经验库。
7. 典型案例库。

知识库负责回答：

```text
为什么推荐这个运动？
为什么限制这个动作？
这个强度依据是什么？
慢病人群需要注意什么？
传统功法如何纳入处方？
专家常见修改意见如何沉淀？
```

知识库和规则库需要独立建设、统一调用，并设置版本管理机制。总体建设方案中也明确指出，知识库解决“处方依据是什么”，规则库解决“什么情况下不能出方、怎样安全出方”。

------

### 8.5 大模型处方生成模块

大模型不直接自由问答，而是在系统约束下生成结构化处方。

生成流程为：

```text
结构化用户数据
  ↓
风险等级
  ↓
人群分型
  ↓
处方模板
  ↓
规则限制
  ↓
知识库证据
  ↓
大模型生成 FITT-VP 处方初稿
  ↓
JSON Schema 校验
  ↓
规则二次安全校验
  ↓
保存 AI 初稿
```

输出结构必须包含：

1. 运动目标。
2. 运动类型。
3. 运动频率。
4. 运动强度。
5. 单次时间。
6. 每周总量。
7. 进阶方式。
8. 注意事项。
9. 禁忌动作。
10. 复测周期。

------

### 8.6 专家审核模块

专家审核是产品上线的核心安全机制。

审核对象包括：

1. R2 中风险用户。
2. 规则冲突处方。
3. 数据异常用户。
4. 专家抽查用户。
5. 反馈预警用户。
6. 需要处方调整用户。

专家审核结果包括：

1. 批准发布。
2. 修改后发布。
3. 驳回重生成。
4. 要求补充数据。
5. 建议医学评估。
6. 建议暂停运动。

------

### 8.7 运动反馈与动态调整模块

平台必须避免一次性出方。每份处方应设置执行周期，一般采用 2—4 周小调整、8—12 周阶段评估。系统根据完成率、RPE、疼痛变化、血压血糖反应和复测结果，自动判断维持、进阶、降级、暂停或进入专家复核。

反馈判断逻辑如下：

| 反馈情况                      | 系统建议                     |
| ----------------------------- | ---------------------------- |
| 完成率 ≥80%，RPE 适中，无不适 | 维持或小幅进阶               |
| 完成率 <50%                   | 降低频率、时长或更换运动项目 |
| RPE 持续偏高                  | 降低强度或缩短时长           |
| 运动后疼痛加重                | 暂停相关动作，进入专家复核   |
| 出现胸闷、头晕、心悸          | 触发红色预警，建议医学评估   |
| 血糖波动明显                  | 进入专家复核流程             |
| 连续 4 周无改善               | 调整处方目标、强度或运动类型 |

对接方式：

```text
借鉴工程结构、Docker、CI/CD、OpenAPI 和权限认证方式；
业务模块全部重写为运动处方平台模块；
不直接复制模板中的业务代码。
```

### 10.2 运动动作库

参考 `yuhonas/free-exercise-db`。该项目提供公开领域的 JSON 运动动作数据，包含 800+ 个动作，并带有可搜索前端和 Unlicense 许可。([GitHub](https://github.com/yuhonas/free-exercise-db?utm_source=chatgpt.com))

对接方式：

```text
将其作为基础动作数据来源；
导入后进行中文化、本地化、风险等级标注、禁忌标签标注；
默认导入状态为“待专家审核”；
审核通过后进入本平台运动项目库。
```

### 10.3 可穿戴设备数据

参考 `the-momentum/open-wearables`。该项目提供自托管的可穿戴数据统一 API，支持多来源健康数据聚合和 AI-ready 健康上下文。([GitHub](https://github.com/the-momentum/open-wearables?utm_source=chatgpt.com))

对接方式：

```text
第一版先预留设备数据接口；
运动反馈支持手动录入和设备数据回传两种来源；
第二阶段对接统一可穿戴设备中台，接入心率、步数、活动时长、睡眠等指标。
```

### 10.4 RAG / GraphRAG 知识库

参考 `stevereiner/flexible-graphrag`。该项目支持文档处理、知识图谱、向量数据库、搜索引擎、LLM / embedding provider、FastAPI 后端和多种前端。([GitHub](https://github.com/stevereiner/flexible-graphrag?utm_source=chatgpt.com))

对接方式：

```text
第一版采用轻量 RAG：文档上传、切片、向量化、检索、证据引用；
后续如需复杂知识图谱和多跳推理，再扩展 GraphRAG 能力；
避免第一期引入过高复杂度影响上线。
```

## 十六、风险控制方案

### 16.1 运动安全风险

风险：AI 生成不适宜运动建议。

控制措施：

```text
规则引擎前置；
R3 不生成训练计划；
R2 必须专家审核；
大模型输出后进行二次规则校验；
所有处方版本留痕。
```

### 16.2 医疗合规风险

风险：平台被误解为医疗诊断系统。

控制措施：

```text
设置知情同意；
明确免责声明；
不诊断疾病；
不调整药物；
不承诺疗效；
高风险用户提示医学评估。
```

### 16.3 数据隐私风险

风险：健康数据泄露或科研导出不规范。

控制措施：

```text
角色权限控制；
最小权限访问；
科研数据脱敏；
导出审批；
操作审计日志；
数据库备份与访问控制。
```

总体方案中也明确要求知情同意、数据最小化、脱敏处理、访问控制和安全审计。

### 16.4 技术实现风险

风险：大模型输出不稳定，影响上线质量。

控制措施：

```text
使用结构化 JSON 输出；
设置 JSON Schema 校验；
Prompt 模板版本管理；
RAG 知识库提供依据；
失败时回退到模板规则生成；
处方发布前强制安全校验。
```

## 十九、决策建议

建议将本项目按“产品化平台 + 示范应用 + 科研成果”三条线同步推进。

第一，产品化平台应优先保证可上线、可使用、可审核、可留痕，不追求第一版算法复杂度过高。

第二，安全机制应作为立项和验收红线，特别是 R2 专家审核、R3 禁止训练处方、大模型输出二次校验。

第三，第一版应控制范围，优先完成用户建档、风险分级、AI 处方初稿、专家审核、处方发布、运动反馈和统计看板。

第四，开源系统只作为工程和数据能力借鉴，不应直接拼装成平台；核心业务规则、处方模板、风险分级和专家审核流程必须自主建设。

第五，建议用 7 周左右完成第一版产品上线，并选择高校或社区场景开展试点。试点完成后，再扩展可穿戴设备、姿态识别、GraphRAG、移动端和多机构 SaaS 能力。

## 二十、总结

本项目拟建设的不是一个“AI 生成运动建议”的演示系统，而是一套以 **数据标准为基础、风险规则为底线、聚类分型为支撑、知识库为依据、大模型为生成工具、专家审核为保障、运动反馈为闭环** 的产品级 AI 运动处方平台。其建设完成后，可支撑真实用户服务、专家协同审核、示范应用推广和科研成果沉淀。
