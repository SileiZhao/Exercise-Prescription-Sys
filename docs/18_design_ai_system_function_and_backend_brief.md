# 启衡运动处方系统功能与后端逻辑设计说明

> 用途：本文档面向后续负责全站视觉与交互重设计的设计 AI。请根据本文描述重新设计系统所有页面的布局、颜色、组件、动画和背景，但不要改变后端业务规则、角色权限、风险状态机和审计逻辑。

## 1. 产品定位

启衡运动处方系统是一个面向医疗运营、运动处方专家、平台管理员、机构管理员和科研人员的临床运动干预中台。它不是消费级健身 App，也不是营销型官网；它服务于受监管医疗场景中的建档、风险分级、个性化运动处方生成、专家审核、运动反馈、阶段复评、规则/模板/知识治理和脱敏科研导出。

设计目标是让用户在每个页面都能先看到安全边界，再执行任务。页面需要表现“风险可解释、处方可审核、资料可追溯、导出可审计”的工作方式。系统中的 AI 只承担辅助生成和检索，不应被设计成无边界的自动决策者。

## 2. 设计 AI 使用方式

设计 AI 应把本文当作产品需求和交互蓝图，而不是代码说明。页面可以重新设计，但必须保留：

- 角色入口与权限边界。
- R0、R1、R2、R3 风险分级语义。
- R2 必须专家审核后发布。
- R3 不生成可执行训练处方，只展示医学评估、转介或暂停运动建议。
- 处方生成必须依赖建档、风险规则、分型、模板、动作候选、RAG 证据和安全校验。
- 运动打卡必须绑定最新有效已发布处方。
- 反馈可能触发处方进阶、降级、专家复核、暂停或转介。
- 科研导出必须走脱敏、申请、审批、限时下载和审计。
- 所有治理动作都应有状态、版本、来源或审计线索。

## 3. 当前技术栈与运行入口

前端技术栈：

- React + Vite。
- Ant Design 作为主要控件体系。
- ECharts 用于图表。
- lucide-react 用于产品图标。
- framer-motion 已引入，可用于状态过渡和轻量动效。
- 路由已做懒加载，页面通过 `frontend/src/routeLoaders.ts` 动态导入。

后端技术栈：

- FastAPI。
- PostgreSQL 作为业务数据库。
- Redis、Qdrant、MinIO 参与缓存、向量检索、对象存储等部署能力。
- Alembic 管理数据库迁移。
- LLM Provider、Embedding Provider、OCR Provider 可配置。
- `/ready` 会检查 LLM、Embedding、OCR、Qdrant 等运行依赖。

运行入口：

- 前端：`http://100.99.170.46:5173/`。
- 后端就绪检查：`http://100.99.170.46:8000/ready`。
- 后端 API 前缀：`/api/v1`。

## 4. 全局信息架构

系统按角色拆成 5 类入口：

| 角色 | 前端身份 | 核心任务 | 设计重点 |
| --- | --- | --- | --- |
| 公开访客 | public | 首页、登录、注册 | 清楚说明系统是临床运动处方中台，避免营销感 |
| 普通用户 | USER | 建档、风险结果、处方、今日运动、反馈、阶段报告 | “今日是否能运动”优先于图表和装饰 |
| 专家 | EXPERT | 分诊看板、审核队列、单任务审核 | 高风险优先级、证据核对、固定发布动作 |
| 管理员 | ADMIN | 运营指挥台、规则、模板、动作、知识、用户、审计、科研审批 | 上线阻断和治理状态优先 |
| 机构管理员 | ORG_ADMIN | 机构范围内管理、审核、导出审批、用户治理 | 强调机构隔离和范围说明 |
| 科研人员 | RESEARCHER | 脱敏总览、分型分析、干预效果、导出申请/下载 | 聚合、脱敏、审批和解释边界 |

## 5. 核心业务闭环

主流程如下：

1. 用户注册或登录。
2. 用户完成知情同意。
3. 用户完成六类健康数据建档。
4. 系统根据健康快照运行风险规则，输出 R0/R1/R2/R3。
5. 系统对用户进行规则分型和可选聚类分型。
6. 系统按风险等级、分型标签、运动目标匹配已批准处方模板。
7. 系统检索知识库证据和已批准动作候选。
8. LLM 生成结构化 FITT-VP 处方草稿。
9. 后端安全校验对处方草稿做不可绕过的兜底处理。
10. R0/R1 可自动发布，R2 进入专家审核，R3 进入转介或医学评估状态。
11. 专家可领取任务、查看用户摘要、核对规则证据、编辑处方、批准、驳回、要求补充资料、暂停或转介。
12. 用户只可执行最新有效已发布处方。
13. 用户提交运动反馈。
14. 反馈调整服务根据红旗信号、RPE、疼痛、完成率、血压、血糖等动态调整处方状态。
15. 阶段报告汇总反馈、安全事件和指标变化。
16. 科研人员只能查看脱敏聚合数据，导出需提交用途，管理员或机构管理员审批后限时下载。

## 6. 后端架构总览

后端入口位于 `backend/app/main.py`：

- 创建 FastAPI 应用。

## 7. 鉴权与权限逻辑

后端使用 Bearer Token 鉴权：

- 密码使用 PBKDF2-SHA256 哈希。
- Access Token 为 HMAC JWT。
- `get_current_user` 从 Token 中解析用户 ID，检查用户是否存在、是否激活。
- 若用户 `must_change_password=true`，除 `/auth/change-password`、`/auth/logout`、`/users/me` 外，其他接口全部返回 403。
- `require_roles(...)` 控制角色权限。

角色权限概览：

| 模块 | 可访问角色 |
| --- | --- |
| 登录、注册、刷新、退出 | 公开或已登录 |
| `/users/me` | 已登录用户 |
| 六类健康数据、风险评估、处方生成、个人处方、今日反馈、个人报告 | 已登录用户，前端主要限制为 USER |
| 专家审核队列和详情 | EXPERT、ADMIN、ORG_ADMIN |
| 管理看板、审计日志、用户治理 | ADMIN、ORG_ADMIN |
| 风险规则创建/更新 | ADMIN |
| 风险规则列表/测试 | ADMIN、EXPERT、ORG_ADMIN 视接口而定 |
| 动作和模板创建/更新 | ADMIN |
| 动作审核 | ADMIN、EXPERT |
| 知识文档创建/上传/重建索引 | ADMIN |
| 知识文档列表/搜索 | ADMIN、EXPERT、ORG_ADMIN |
| 聚类训练和启用 | ADMIN |
| 聚类模型列表 | ADMIN、RESEARCHER、ORG_ADMIN |
| 科研汇总、申请、下载 | RESEARCHER、ADMIN、ORG_ADMIN |
| 科研导出审批 | ADMIN、ORG_ADMIN |

设计要求：权限不足、首次登录需改密、Token 失效、机构范围不匹配都要有明确错误态，不要只弹出模糊“失败”。

## 8. 核心数据对象

### 8.1 用户与机构

主要模型：

- `User`：邮箱、手机号、姓名、角色、机构、激活、验证、首次改密状态。
- `Organization`：机构名称、类型、联系人、电话、地址、状态。
- `ExpertProfile`：专家用户、职称、专业方向、证书编号、简介、每日审核量。
- `UserConsent`：知情同意版本、文本、是否有效、接受时间。

设计语义：

- 用户不是社交成员，而是受权限约束的工作台身份。
- 机构是数据范围和审批范围的边界。
- 专家资料决定审核能力，不能被设计成普通个人资料页。

### 8.2 六类健康数据

主要模型：

- `UserProfile`：姓名、性别、生日、年龄、身高、体重、BMI、腰臀比、职业、久坐、睡眠、运动目标、运动习惯、运动经验。
- `FitnessTest`：静息心率、血压、肺活量、握力、柔韧、平衡、反应、台阶测试、6 分钟步行、疼痛评分、基础 RPE。
- `BodyComposition`：体脂、骨骼肌、肌肉量、去脂体重、内脏脂肪、基础代谢、身体水分、骨量、蛋白、体型、设备型号。
- `BiochemicalIndex`：空腹血糖、餐后 2 小时血糖、HbA1c、血脂、尿酸、肌酐、ALT、AST、血红蛋白、血氧。
- `RiskScreening`：慢病、疼痛、损伤、手术史、用药、胸痛、晕厥、异常气短、心悸、医生限制、PAR-Q+。
- `ExerciseFeedback`：运动日期、项目、频次、时长、强度、心率、运动前后血压、血糖、RPE、完成率、不适、疼痛。

后端规则：

- 保存任何健康数据前必须存在有效知情同意。
- 基础档案保存时自动计算年龄、BMI、腰臀比。
- 基础档案每次更新会写入 `UserProfileMeasurement`，用于阶段变化计算。
- 生成健康快照时，基础档案是必需项；其他数据可为空，但会进入完成度判断。
- 运动反馈必须绑定最新有效已发布处方，不能随便打卡。

### 8.3 风险与处方

主要模型：

- `RiskRuleConfig`：管理员配置的风险规则。
- `PrescriptionRecord`：风险等级、分型、目标、FITT-VP、注意事项、禁忌、复评安排、证据、LLM 输入、状态、是否需专家审核、版本、父版本。
- `PrescriptionVersion`：处方版本快照、变更原因、操作者。
- `PrescriptionEvidence`：风险规则、模板引用、动作引用、RAG 切片、LLM Provider、模型、结构校验、安全校验、对象引用。
- `ExpertReview`：审核单、专家、状态、意见、编辑后的处方、动作、审核时间。

处方状态语义：

| 状态 | 含义 | 用户端表现 |
| --- | --- | --- |
| `PUBLISHED` | 已发布，可执行 | 可进入今日运动 |
| `PENDING_REVIEW` | 待专家审核 | 锁定执行入口，提示等待审核 |
| `IN_REVIEW` | 审核中 | 显示专家正在处理 |
| `NEEDS_INFO` | 需补充资料 | 引导补充建档或等待说明 |
| `PAUSED` | 暂停运动 | 阻断训练入口，展示暂停原因 |
| `REFERRED` | 医学评估/转介 | R3 或红旗信号，不能训练 |
| `REJECTED` | 被驳回 | 显示原因，通常需要重生成或补充资料 |
| `SUPERSEDED` | 历史版本 | 只可查看，不能执行 |

### 8.4 内容治理

主要模型：

- `ExerciseAction`：动作名称、类型、风险等级、适宜标签、禁忌标签、动作说明、替代动作、常见错误、监测提示、停止信号、证据引用、审核状态。
- `PrescriptionTemplate`：模板编码、名称、风险等级、分型标签、目标标签、FITT-VP、注意事项、禁忌、证据引用、状态、版本、来源版本、平台审核状态。
- `KnowledgeDocument` 与 `KnowledgeChunk`：知识文档和切片，支持向量检索和关键词 fallback。
- `ComplianceDocument`：合规文案或材料，记录确认状态。

内容治理原则：

- 新增动作默认进入 `PENDING_REVIEW`，批准后才参与处方候选。
- 只有已批准模板参与自动匹配。
- R3 模板不能包含 FITT-VP。
- 知识文档启用后尝试写入 Qdrant 向量索引，失败时标记 `INDEX_FAILED`，关键词检索可 fallback，但生产环境处方生成会因为 RAG 降级被阻断。

### 8.5 聚类与科研

主要模型：

- `ClusterModel`：模型名称、算法、簇数、特征、缩放参数、模型参数、簇画像、评估指标、来源、状态。
- `UserClusterAssignment`：用户分型结果、规则标签、聚类标签、画像总结、是否覆盖风险。
- `ResearchExportRequest`：申请人、机构范围、格式、用途、状态、审批人、审批意见、样本量、快照、过期时间、下载时间。

设计语义：

- 聚类只用于健康画像和模板匹配，不能覆盖风险规则。
- 科研数据必须脱敏和聚合，不展示姓名、手机号、身份证或真实身份字段。
- 科研导出审批通过后 24 小时内可下载，下载会记录审计，过期或已下载后不应继续突出下载入口。

## 9. 风险引擎逻辑

风险引擎输入是健康快照，输出 `RiskEvaluationResult`：

- `risk_level`：R0、R1、R2、R3。
- `message`：风险结论文案。
- `allow_ai_generation`：是否允许生成处方。
- `allow_auto_publish`：是否允许自动发布。
- `requires_expert_review`：是否需要专家审核。
- `intensity_cap`：强度上限。
- `contraindications`：禁忌和限制。
- `matched_rules`：命中的规则。
- `source_snapshot`：来源快照。

后端规则来源有两层：

1. 内置规则 `BUILTIN_RULES`。
2. 管理员配置并启用的 `RiskRuleConfig`。

严重度映射：

| 严重度 | 风险等级 | 处方策略 |
| --- | --- | --- |
| RED | R3 | 不生成训练处方，只输出安全提醒、医学评估或转介建议 |
| YELLOW | R2 | 可生成谨慎型系统初稿，但必须专家审核后发布 |
| GREEN | R1 | 可自动生成改善型处方，后台可抽查 |
| 无命中 | R0 | 可自动生成基础处方 |

典型内置规则：

- 胸痛、晕厥、严重气短、严重高血压、疼痛 7 分以上、医生明确限制、近期急性损伤会触发 RED，进入 R3。
- 高血压、糖尿病、疼痛 4-6 分、影响运动反应的用药、血压黄色阈值会触发 YELLOW，进入 R2。
- BMI >= 24 等低风险改善指标触发 GREEN，进入 R1。

设计要求：

- R0/R1/R2/R3 必须同时用文字、图标、颜色和行动说明表达。
- R3 页面不允许出现“开始训练”“生成训练计划”之类行动按钮。
- R2 页面必须展示“待专家审核/审核中/需补充资料”等状态，不要让用户误以为可直接执行。
- 风险规则命中要能追溯到字段路径、命中文案、禁忌和后续动作。

## 10. 处方生成后端逻辑

处方生成由 `PrescriptionOrchestrator.generate_for_user` 编排：

1. 调用风险评估。
2. 若 R3：
   - 不调用普通模板匹配和 LLM 生成训练计划。
   - 构造“高风险转介型”记录。
   - `fitt_vp=null`。
   - 状态为 `REFERRED`。
   - `expert_review_required=true`。
3. 若 R0/R1/R2：
   - 调用聚类分型。
   - 读取用户运动目标。
   - 按风险等级、分型标签和目标匹配已批准模板。
   - 检索禁忌参考资料。
   - 使用 RAG 检索知识证据。
   - 筛选已批准动作候选，并排除禁忌冲突和禁止动作类别。
   - 构造 LLM 输入 payload。
   - 调用 LLM 生成 `PrescriptionDraft`。
   - 记录 LLM 生成审计。
   - 调用 `enforce_prescription_safety` 做安全校验。
   - R2 状态为 `PENDING_REVIEW`，R0/R1 状态为 `PUBLISHED`。
   - 写入处方、版本、证据和审计。

生产环境阻断条件：

- 缺少已批准模板。
- 缺少已批准动作候选。
- 没有检索到可追溯 RAG 证据。
- RAG 向量检索降级为关键词 fallback。

安全校验逻辑：

- R3 强制清空 FITT-VP，状态转介，禁忌为“禁止生成具体运动强度、训练动作、组数、时长和进阶计划”。
- R2 过滤高强度、HIIT、冲刺、大重量、憋气等词。
- 疼痛相关禁忌会过滤跳跃、长跑、深蹲、快速扭转、大重量。
- 高血压相关禁忌会过滤憋气、大重量。
- 糖尿病或降糖药/胰岛素场景会追加运动前后血糖监测提醒。
- 处方动作类型会被限制在候选动作或模板动作内，防止 LLM 自行加入高风险动作。

设计要求：

- 处方页需要展示“生成链路”：风险规则、分型、模板、动作候选、RAG 证据、安全校验、发布状态。
- 不能把 LLM 生成表现成完全自动可信，应突出系统初稿、专家审核和证据链。
- 处方详情必须把 FITT-VP、禁忌、注意事项、安全提示放在同一工作区，避免用户只看到训练内容。

## 11. 专家审核后端逻辑

专家审核由 `ExpertReviewService` 处理。审核队列包含以下处方状态：

- `PENDING_REVIEW`
- `IN_REVIEW`
- `REFERRED`
- `NEEDS_INFO`
- `PAUSED`

队列可按风险等级、状态、机构、处方类型、异常反馈、日期筛选。专家只能处理自己机构内任务；任务若已分配给其他专家，当前专家不能处理。管理员可跨机构或按机构查看。

审核动作：

| 动作 | 后端影响 | 设计表现 |
| --- | --- | --- |
| 开始审核 | 创建或更新审核单，专家领取，处方状态转 `IN_REVIEW` | 写入审计，解锁编辑 |
| 批准 | 安全校验专家编辑，处方状态转 `PUBLISHED`，版本 +1 | 发布前二次确认 |
| 驳回 | 审核单 `REJECTED`，处方 `REJECTED` | 要求清楚原因 |
| 医学评估/转介 | 审核单和处方转 `REFERRED`，清空 FITT-VP | R3 或红旗场景使用 |
| 要求补充资料 | 审核单和处方转 `NEEDS_INFO` | 用户端提示补充资料 |
| 暂停运动 | 审核单和处方转 `PAUSED` | 用户端阻断运动 |

审核详情数据：

- 处方记录。
- 审核单。
- 用户健康快照。
- 命中风险规则。
- RAG 证据。
- 模板来源。
- 候选动作。
- 版本历史。
- 趋势摘要。

设计要求：

- 专家端不是表单页，而是“优先级队列 + 单任务证据工作台”。
- 首屏应优先显示 R3、异常反馈、超时和待领取任务。
- 单任务详情应采用左右或三栏工作台：用户安全摘要、处方编辑、规则证据/审计。
- R3 任务必须隐藏训练处方编辑字段，只显示医学评估/转介处理。
- 批准按钮应固定在可见区域，但必须经过“已核对风险规则、禁忌动作和处方强度”的确认。

## 12. 反馈调整与阶段评估逻辑

运动反馈提交后，可调用 `FeedbackAdjustmentService.adjust_after_feedback` 动态调整处方。反馈必须绑定最新有效已发布处方。

判定因素：

- 红旗不适：胸痛、胸闷、晕厥、头晕、黑蒙、严重气短、喘憋、心悸。
- 运动前血压 >= 180/110。
- 运动前血糖 < 3.9 或 > 16.7。
- 最大心率 >= 200。
- 运动后疼痛 >= 7。
- 运动后疼痛 >= 4 或不适包含疼痛。
- RPE >= 17，连续高 RPE 风险更高。
- 完成率 < 60。
- 完成率 >= 85 且无不适且 RPE <= 6。

动作映射：

| 反馈判定 | 后端动作 | 处方影响 |
| --- | --- | --- |
| `RED_ALERT` | 红色预警 | 风险转 R3，状态 `REFERRED`，清空 FITT-VP，需专家审核 |
| `REVIEW_REQUIRED` | 需要专家复核 | 状态 `PENDING_REVIEW`，追加安全提示和禁忌 |
| `DEGRADE` | 降级 | 仍可发布，但降低训练负荷 |
| `PROGRESS` | 进阶 | 小幅进阶，不同时大幅增加强度和时间 |
| `MAINTAIN` | 维持 | 维持当前处方并继续观察 |

阶段评估：

- 周期限制 1-12 周，默认 4 周。
- 汇总反馈次数、平均完成率、平均 RPE、疼痛事件、不适事件、红色预警事件。
- 计算体重、BMI、腰围、血压、体脂、骨骼肌、血糖、血脂等前后变化。
- 若无反馈，返回 `NO_DATA`，提示继续打卡。
- 若红色预警，输出暂停训练和医学评估建议。
- 若疼痛或 RPE 偏高，进入专家复核。
- 若完成率低，建议降级。
- 若完成率高且无明显不适，建议小幅进阶。

设计要求：

- 今日运动页必须先展示安全闸门，再展示打卡表单。
- 红旗信号应触发强提醒和中断流程，不应只作为普通多选项。
- 阶段报告应把“决策、反馈安全事件、指标变化、下一阶段建议”放在同一报告结构中。

## 13. 管理治理后端逻辑

### 13.1 管理指挥台

`AdminDashboardService.summary` 返回：

- 用户总数和角色分布。
- 风险分布。
- 处方状态分布。
- 专家审核状态。
- R2 审核率。
- R3 转介数。
- 反馈总数和平均完成率。
- 模板总数和已批准模板数。
- 处方生成/发布趋势。
- 规则命中排行。
- 模板使用排行。
- 聚类分布。
- 上线资料状态。

上线资料状态包含：

- 风险规则总数和启用数。
- 已批准动作数和待审动作数。
- 合规材料确认数和草稿数。
- 模板总数和已批准数。
- 知识文档、跳过文档、索引失败文档、切片、已索引切片。
- LLM Provider、模型、状态和生产就绪。
- Embedding Provider、模型、状态和生产就绪。
- OCR Provider、是否启用、状态。

设计要求：管理端首页应先显示上线阻断、资料就绪和审核积压，再显示 KPI 和图表。

### 13.2 风险规则治理

管理员可以创建、更新、停用风险规则。规则字段包括：

- 规则编码、名称、严重度、优先级、规则类型。
- 来源引用、适用人群、审核状态。
- 命中文案。
- 条件：字段路径、操作符、比较值。
- 禁忌动作或限制。
- 强度上限。
- 是否启用。

规则测试接口使用输入快照运行同一风险引擎，返回风险评估结果。

设计要求：

- 规则编辑是高风险动作，默认应放在抽屉或分步表单。
- 保存前应鼓励运行规则测试。
- 列表需要按编码、风险等级、字段路径、来源、启用状态检索。
- 规则详情需要展示最近命中线索和审计入口。

### 13.3 模板、动作、知识、合规治理

模板库：

- 管理 FITT-VP 模板。
- 模板保存后可进入草稿、批准、归档等状态。
- R3 模板不能包含 FITT-VP。
- 已批准模板才参与自动匹配。

动作库：

- 管理动作及其适宜标签、禁忌标签、停止信号、证据引用。
- 新增动作默认待审核。
- 动作批准后才参与处方候选。

知识库：

- 可创建文本知识文档或上传文件。
- 文档被切片后进入 RAG 检索。
- 可搜索知识证据。
- 可启用/归档文档。
- 可重建向量索引。

合规材料：

- 展示材料编码、标题、审核状态、版本、适用范围。
- 主要用于发布与审计支撑。

设计要求：

- 这组页面应采用“治理工作台”而非普通表格堆叠。
- 动作、模板、知识三类对象都需要列表、筛选、详情、编辑、版本历史和审计留痕。
- 新增/编辑动作应使用抽屉，避免主页面被长表单占满。
- 知识库要清楚展示索引状态，尤其 `INDEX_FAILED` 和关键词 fallback 的风险。

### 13.4 聚类模型生命周期

聚类模型支持：

- 训练模型。
- 查看模型指标。
- 启用模型。
- 归档模型。
- 分类当前用户。

训练逻辑：

- 使用年龄、BMI、腰围、久坐、静息心率、血压、疼痛、单脚站立、体脂、骨骼肌、内脏脂肪、血糖、血脂等特征。
- 样本不足时使用规则原型做 bootstrap。
- 支持 KMeans、DBSCAN、GaussianMixture、AgglomerativeClustering。
- 评估指标包括 silhouette、Davies-Bouldin、稳定性、最小簇占比等。
- 启用新模型时会归档其他 active 模型。
- 模型评估未达标不能启用。

分型逻辑：

- 规则分型会生成“肥胖代谢风险型”“心肺功能不足型”“肌力不足型”“老年功能下降型”“损伤风险限制型”“初级运动水平”“普通健康维持型”等标签。
- 聚类模型可补充提示，但不能覆盖风险规则。

设计要求：

- 页面标题和说明必须反复强调：聚类只用于画像和模板匹配，不覆盖 R0-R3 风险规则。
- 模型生命周期应清晰展示训练中、已训练、已启用、已归档。
- 指标解释需要通俗，不要只展示机器学习名词。

### 13.5 身份治理与审计

用户治理支持：

- 用户列表、分页、角色/机构/关键词筛选。
- 修改角色、机构、激活、验证状态。
- 创建机构。
- 创建和维护专家资料。

审计日志支持：

- 按动作、资源、操作者、时间筛选。
- 查看完整 metadata。
- 重点追踪规则、处方、资料、导出和身份治理。

设计要求：

- 用户治理需要突出“角色影响工作台可见范围”。
- 机构 ID 或机构名称要作为范围边界，不要弱化。
- 审计日志要像调查工具，支持快速过滤和详情抽屉。

## 14. 科研导出后端逻辑

科研导出由 `ResearchExportService` 处理。

角色范围：

- ADMIN：全局范围。
- ORG_ADMIN：本机构范围。
- RESEARCHER：本人机构范围，并且只能看本人导出申请。

科研总览返回：

- 脱敏参与者数。
- 风险分布。
- 分型分布。
- 分型与风险叠加。
- 处方状态分布。
- 模板效果。
- 导出任务状态。
- 干预效果：反馈数、平均完成率、平均 RPE、不适事件、疼痛加重、完成率趋势、RPE 趋势、疼痛趋势、血压趋势、血糖趋势。

脱敏行数据包含：

- 研究编号或参与者编码。
- 年龄段而非精确身份。
- 性别、身高、体重、BMI、腰围、腰臀比。
- 体测、生化、慢病风险摘要。
- 风险等级、处方目标、FITT-VP 摘要。
- 平均完成率、RPE、疼痛变化、不良事件、调整次数、阶段变化、依从性趋势。

导出申请状态：

| 状态 | 含义 | 设计表现 |
| --- | --- | --- |
| `PENDING` | 已提交，待审批 | 研究人员不可下载，管理员可审批 |
| `APPROVED` | 已批准 | 在有效期内显示下载 |
| `REJECTED` | 已驳回 | 显示审批意见和重新申请建议 |
| 已过期 | `expires_at` 已过 | 不可下载 |
| 已下载 | `downloaded_at` 有值 | 显示已下载和审计说明 |

审批逻辑：

- 创建申请时记录用途、格式、样本量和机构范围。
- 审批通过时写入快照数据，设置 24 小时过期时间。
- 驳回时写入审批意见。
- 下载时根据格式生成 CSV、XLSX 或 JSON，并记录 `downloaded_at` 和审计日志。
- 下载必须满足：状态已批准、未过期、角色和机构范围匹配。

设计要求：

- 科研端页面必须反复表达“脱敏聚合”和“非本人申请不可见”。
- 管理端科研审批只展示用途、格式、样本量、状态、过期时间、审批意见和敏感字段检查。
- 审批意见不能只写“同意”或“驳回”，界面应提示最小说明要求。
- 下载按钮只在确实可下载时明显展示。

## 15. 报告导出逻辑

报告服务支持：

- 处方报告 DOCX。
- 处方报告 PDF。
- 阶段评估报告 DOCX。
- 阶段评估报告 PDF。
- 用户查看自己的报告导出记录。

报告内容包含：

- 分型。
- FITT-VP。
- 注意事项。

## 16. 前端页面与设计说明

### 16.1 公开首页 `/`

当前职责：

- 作为角色控制台入口。
- 展示用户端、专家端、管理端、科研端 4 个工作台。
- 若已登录，根据 `current_user_role` 推荐当前角色入口。
- 展示风险分级、证据链路、科研治理等平台信号。

设计要求：

- 首页不是营销落地页，第一屏应像“受控工作台入口”。
- 背景可使用轻量临床网格、数据层、处方流程线或风险分级轨道，但不要用大幅商业插画。
- 需要让用户一眼理解：这是运动处方、风险分级、专家审核、科研治理系统。
- 一屏内应完整展示品牌、登录/注册、角色入口和关键安全边界，不要让核心登录区域需要下滑。
- 使用克制的临床色，不要霓虹、玻璃拟态、健身房风格或营销大标题。

### 16.2 登录页 `/login`

当前职责：

- 邮箱和密码登录。
- 登录成功保存 access token、refresh token、用户角色、姓名、邮箱、机构。
- 若 `must_change_password=true`，跳转 `/auth/change-password`。
- 根据角色跳转对应工作台。

设计要求：

- 登录页应强调“安全进入工作台”，不是普通账户营销页。
- 表单应稳定、清晰、可自动填充。
- 背景可以表现安全流程、角色分流和临床网格，但表单不可被背景干扰。
- 错误态必须明确，显示登录失败原因。

### 16.3 注册页 `/register`

当前职责：

- 普通用户注册。
- 字段：邮箱、姓名、手机号、密码。
- 注册成功后跳转用户看板。

设计要求：

- 注册不是多角色开户，文案需说明注册后进入普通用户路径。
- 强调后续需要完成知情同意和健康建档。

### 16.4 首次改密页 `/auth/change-password`

当前职责：

- 首次登录或被要求改密时，输入当前密码和新密码。
- 改密成功后按角色进入对应工作台。

设计要求：

- 视觉应严肃简洁。
- 强调这是安全确认流程，不是普通设置页。

### 16.5 用户通行证 `/user/dashboard`

当前职责：

- 用户首页，回答“今天是否可以运动”。
- 展示当前风险等级、专家审核状态、今日可运动、阻断原因。
- 展示本周完成率、建档完成率、阶段目标、最近反馈、监测提醒、处方版本、下次复评日期、连续打卡天数、异常反馈数。
- 展示处方摘要、FITT-VP、风险规则命中、计划完成趋势、反馈趋势、健康画像雷达。

设计要求：

- 第一屏必须是通行证决策，不是图表墙。
- 若不可运动，阻断原因应最醒目。
- 风险、审核、处方可见性和下一步行动必须同屏。
- 趋势图和雷达图放在次级区域，缺数据时用解释型空态。
- 用户未建档、未生成处方、处方待审、R3 转介、暂停运动都要有不同状态。

### 16.6 用户建档 `/user/onboarding`、`/user/profile`、`/user/health-data`

当前职责：

- 分步收集知情同意、基础档案、体测、体成分、生化指标、风险筛查。
- 支持本地草稿。
- 保存当前步骤。
- 完成后可生成风险结果。

页面步骤：

1. 知情同意。
2. 最小建档信息。
3. 体型与生活方式。
4. 运动目标与经验。
5. 运动前生命体征。
6. 体质测试增强项。
7. 体成分指标。
8. 生化指标。
9. 慢病、疼痛、用药、医生限制和红旗信号。

设计要求：

- 使用清晰的分步导航和固定的临床解释面板。
- 必填和选填要分层，不要一次铺满所有字段。
- 红旗信号应独立成高优先级区域。
- 每步要有保存、返回、下一步、草稿提示和校验错误。
- 表单密度可以高，但分组必须明确。

### 16.7 风险结果 `/user/phenotype`、`/user/risk-result`

当前职责：

- 运行或展示当前用户风险评估和分型。
- 显示 R0/R1/R2/R3 安全边界。
- 显示分型标签和下一步动作。
- 强调分型只用于模板匹配，不覆盖风险规则。

设计要求：

- 页面像一份风险判定报告。
- 风险结论在上，规则和证据在下。
- R2 引导等待专家审核或查看审核状态。
- R3 引导医学评估或转介，不展示运动训练行动。
- 分型标签应作为辅助信息，视觉层级低于风险等级。

### 16.8 处方页 `/user/prescriptions`、`/user/prescriptions/:id`

当前职责：

- 查询个人处方列表和最新处方。
- 生成处方。
- 展示发布状态、安全提示、FITT-VP、禁忌、注意事项、证据和版本。
- 导出处方报告 DOCX/PDF。
- 查看报告导出记录。

设计要求：

- 未发布或 R3 状态自动锁定训练计划。
- 处方内容要以“可执行结构 + 安全边界”形式出现。
- FITT-VP 可以设计为 6 个稳定信息单元：频率、强度、时间、类型、总量、进阶。
- 禁忌、注意事项和安全提示要靠近训练内容。
- 生成按钮需要根据建档、风险和处方状态禁用或给出原因。
- 历史版本和导出记录作为次级信息展示。

### 16.9 今日运动 `/user/today`、`/user/feedback`

当前职责：

- 检查是否存在可执行处方。
- 显示今日处方任务。
- 提交运动反馈。
- 红色安全中断。
- 联系专家/医生或查看医学评估建议。

反馈字段：

- 运动日期、项目、本周第几次、时长、主观强度、RPE、完成率、疼痛评分、不适反应、运动前后血压、血糖、心率。

设计要求：

- 页面第一模块必须是“运动前安全闸门”。
- 没有可执行处方时，不显示普通打卡表单。
- 红旗不适选择后应阻止普通提交，改走中断或联系专家路径。
- 反馈表单可放在抽屉，避免主界面过长。
- 当前处方版本必须可见，避免用户执行历史版本。

### 16.10 阶段报告 `/user/phase-report`、`/user/follow-up-report`

当前职责：

- 获取 4 周或指定周期阶段评估。
- 展示阶段决策、反馈次数、平均完成率、平均 RPE、疼痛事件、不适事件、红色预警事件。
- 展示阶段指标对比和反馈趋势。
- 导出 DOCX/PDF。

设计要求：

- 结构像复评报告，而不是普通数据看板。
- 先显示阶段决策，再显示图表。
- 缺失数据要展示“为什么不可计算”，不要渲染空图。
- 下一阶段建议要靠近决策区。

### 16.11 专家分诊 `/expert/dashboard`

当前职责：

- 专家工作台首页。
- 显示 R3、异常反馈、超时、待领取任务。
- 显示审核统计：平均审核小时、R2 待审、超时数。
- 显示队列结构和优先处理说明。

设计要求：

- 像临床分诊 inbox。
- R3 和异常反馈优先级最高。
- 列表项需要显示处方 ID、用户 ID、风险、状态、异常反馈数、版本、创建时间。
- 不要把专家首页做成普通 KPI 大屏，必须能直接处理任务。

### 16.12 专家审核 `/expert/reviews`、`/expert/reviews/:id`

当前职责：

- 队列筛选。
- 领取任务。
- 查看单个审核详情。
- 编辑 FITT-VP、注意事项、禁忌、复评、安全提示。
- 查看系统初稿、结构化差异、规则证据、RAG 证据、候选动作、审计。
- 执行批准、驳回、要求补充资料、医学评估/转介、暂停运动。

设计要求：

- `/expert/reviews` 是队列页，`/expert/reviews/:id` 是单任务工作台。
- 单任务页建议三栏或左右分栏：用户摘要、处方编辑、证据审计。
- 领取前可只读预览，开始审核后解锁编辑。
- R3 任务不显示训练编辑器。
- 发布按钮需固定但受状态约束，发布前有确认弹窗。

### 16.13 管理指挥台 `/admin/dashboard`

当前职责：

- 展示上线闸口、运行依赖、资料状态、审核积压、R3 转介、处方趋势、规则命中、模板使用、聚类分布。

设计要求：

- 首屏重点：上线阻断和待办异常。
- 运行依赖异常、RAG 索引失败、动作待审、模板不足、合规材料未确认要形成清晰待办。
- 图表分组在标签页或分区内，避免首屏图表墙。

### 16.14 风险规则 `/admin/rules`

当前职责：

- 列表、检索、详情、创建、编辑、测试风险规则。
- 查看审计线索。

设计要求：

- 规则列表密度高但要可扫描。
- “新增规则”和“运行规则测试”是主要操作。
- 规则详情抽屉应展示业务说明、条件、禁忌、强度上限、启用状态、审计。
- JSON 测试快照区域要有格式化和错误反馈。

### 16.15 模板库 `/admin/templates`

当前职责：

- 管理处方模板。
- 查看模板状态、风险等级、匹配范围、FITT-VP、安全边界、证据引用、版本历史和审计。

设计要求：

- 使用主从布局或表格 + 详情抽屉。
- FITT-VP 不要展示为原始 JSON，应拆成可读字段。
- 模板状态、平台审核状态、版本号和来源必须可见。

### 16.16 动作库 `/admin/exercises`

当前职责：

- 管理动作库。
- 导入动作、筛选动作、查看详情、编辑动作、批准或驳回动作。

设计要求：

- 首屏突出待审核动作。
- 动作详情需要展示适宜标签、禁忌标签、停止信号、关节/冲击、证据引用。
- 批准和驳回应有明确按钮和审计提示。

### 16.17 知识库 `/admin/knowledge`

当前职责：

- 创建文本知识文档。
- 上传知识文档。
- 搜索知识证据。
- 启用/归档文档。
- 重建向量索引。
- 展示文档切片数和索引状态。

设计要求：

- 页面要表现“证据治理”，不是普通文件上传。
- 索引失败、关键词 fallback、未启用文档都要有明显状态。
- 搜索结果应展示文档名、切片、分数、来源类型、版本、章节、页码、可信等级。

### 16.18 合规材料

当前职责：

- 在模板治理工作台中展示合规材料列表。
- 字段包括编码、标题、审核状态、版本、适用范围。

设计要求：

- 合规材料是发布和审计支撑，视觉应严肃克制。
- 状态要和模板/知识状态一致。

### 16.19 聚类模型 `/admin/clusters`、`/admin/clustering`

当前职责：

- 训练聚类模型。
- 查看模型生命周期。
- 查看分型分布。
- 查看模型版本和详情。
- 启用或归档模型。

设计要求：

- 强调聚类是辅助分型，不覆盖风险规则。
- 训练入口应低频收起，避免误操作。
- 模型卡片需要显示算法、簇数、来源、评估是否达标、预测策略、噪声或稳定性。
- 启用动作要明显提示会归档其他 active 模型。

### 16.20 身份治理 `/admin/users`

当前职责：

- 用户列表与筛选。
- 修改用户角色、机构、激活、验证状态。
- 新建机构。
- 维护专家资料。
- 查看角色分布。

设计要求：

- 页面应强调权限边界和机构隔离。
- 用户详情、角色修改、机构创建、专家资料维护分成独立抽屉或面板。
- 修改角色是敏感动作，应有确认或审计提示。

### 16.21 审计日志 `/admin/audit-logs`

当前职责：

- 查询审计日志。
- 快速过滤规则、处方、导出、用户治理。
- 表格展示动作、资源、操作者、时间。
- 抽屉展示完整 metadata。

设计要求：

- 这是追溯工具，应支持搜索、筛选、详情展开和 metadata 阅读。
- 不要做成纯装饰时间线，表格可读性更重要。

### 16.22 科研审批 `/admin/research-export`

当前职责：

- 管理员或机构管理员查看导出申请队列。
- 查看用途、格式、样本量、申请人、状态、过期时间、下载状态、审批意见。
- 输入审批意见。
- 批准或驳回申请。
- 查看脱敏字段范围和审计说明。

设计要求：

- 审批页应像风控审批台。
- 左侧申请队列，右侧申请详情和审批意见。
- 敏感字段检查必须明确：不含姓名、手机号、身份证号。
- 审批意见不足时禁用批准/驳回。

### 16.23 科研总览 `/research/dashboard`

当前职责：

- 展示脱敏样本量、反馈记录数、平均完成率。
- 展示分析可用性结论。
- 展示风险分布和干预前后变化。

设计要求：

- 页面要表达“科研端只看脱敏聚合数据”。
- 图表下方应有解释和阈值说明，避免用户把趋势当成个体诊断。

### 16.24 科研分型 `/research/cluster-analysis`

当前职责：

- 展示分型统计。
- 展示分型与风险叠加。
- 展示冷启动说明。

设计要求：

- 分型图表应表现样本规模和分布，不展示个体。
- 样本不足时给出冷启动说明，不渲染空散点图。

### 16.25 科研干预效果 `/research/intervention-effects`

当前职责：

- 展示依从性、主观强度、疼痛/不适、生理趋势。
- 包含完成率趋势、RPE 趋势、疼痛趋势、血压趋势、血糖趋势。

设计要求：

- 使用折叠分组或标签组织，不要一次展示所有图。
- 每个图表都要有“如何解读”和“不代表个体诊断”的边界说明。
- 疼痛和不适优先级高于完成率。

### 16.26 科研导出 `/research/export`、`/research/export-jobs`

当前职责：

- 查看导出前可见范围和审批后下载规则。
- 提交导出申请。
- 查看本人导出任务。
- 下载已批准且未过期的数据包。

设计要求：

- 申请抽屉包含用途、格式、字段范围预览、用途模板。
- 研究人员只能看到本人申请，界面要说明非本人申请不可见。
- 下载按钮只在 `canDownloadExport=true` 时突出。

## 17. 全局视觉设计建议

### 17.1 视觉基调

推荐方向：克制、临床、可信、可审计、任务导向。

避免方向：

- 消费健身 App 风格。
- 营销 landing page 风格。
- 大面积渐变、霓虹、玻璃拟态。
- 过度圆角、软萌卡片、情绪化插画。
- 大量装饰动画。

### 17.2 色彩系统

当前设计 Token：

| Token | 值 | 用途 |
| --- | --- | --- |
| `--color-bg` | `#eef3f7` | 应用背景 |
| `--color-bg-strong` | `#dfe9f0` | 侧栏和页面带 |
| `--color-surface` | `#ffffff` | 主工作面 |
| `--color-surface-muted` | `#f7fafc` | 次级面板 |
| `--color-line` | `#d8e2ea` | 边框和分隔 |
| `--color-ink` | `#132235` | 主文本 |
| `--color-muted` | `#5f7186` | 次级文本 |
| `--color-primary` | `#145c72` | 临床品牌锚点 |
| `--color-action` | `#1d6fd8` | 主操作 |
| `--color-teal` | `#0f766e` | 正向运营状态 |
| `--risk-r0` | `#228b4e` | R0 |
| `--risk-r1` | `#087c83` | R1 |
| `--risk-r2` | `#b76504` | R2 |
| `--risk-r3` | `#bf3030` | R3 |

设计 AI 可以微调色阶，但应保持临床浅色系统，不能让页面变成单一蓝色或单一绿色。风险色必须配文字、图标、行动说明，不能只靠颜色。

### 17.3 布局系统

推荐：

- 桌面端使用侧栏 + 顶部页面头 + 主工作区。
- 用户端首屏使用“通行证/决策卡 + 下一步动作 + 关键摘要”。
- 专家端使用“队列 + 单任务工作台”。
- 管理端使用“上线闸口 + 治理工作区 + 分析图表”。
- 科研端使用“脱敏说明 + 聚合指标 + 申请/审批流程”。
- 抽屉用于低频创建、编辑和详情。
- 表格用于高密度治理对象。
- 标签页或折叠用于多图表研究分析。

避免：

- 大面积卡片堆叠但没有任务优先级。
- 卡片套卡片。
- 所有页面都套同一种 hero。
- 首屏必须下滑才能看到主任务。
- 把医疗安全提醒放在页脚或角落。

### 17.4 组件建议

全局复用组件应覆盖：

- 角色侧栏导航。
- 页面头：当前位置、任务说明、状态徽章、主操作。
- 风险状态徽章。
- 审核状态徽章。
- 运动可执行状态徽章。
- 运行依赖就绪徽章。
- 导出审批状态徽章。
- 决策 Banner。
- 状态 Tile。
- 工作区 Section。
- 数据图表卡。
- 证据卡。
- 审计抽屉。
- 表单分组。
- 空态说明。
- 错误态和重试。

组件状态必须覆盖：

- 默认、悬停、聚焦、按下、禁用、加载、错误、成功。
- 图表加载应使用骨架或保留高度，不要让页面跳动。
- 空态应说明为什么为空和下一步做什么。

### 17.5 动效建议

可使用 framer-motion，但动效必须表达状态变化：

- 路由切换轻微淡入或位移，150-250 ms。
- 抽屉和模态使用 Ant Design 默认或轻微增强。
- 风险状态切换可使用短促强调，但不要弹跳。
- 列表筛选、详情展开、步骤切换可以有空间连续性。
- 加载状态使用骨架或进度，不要全屏炫酷 loading。

必须支持 `prefers-reduced-motion`，动效不能阻塞任务。

### 17.6 背景建议

可用背景元素：

- 极浅临床网格。
- 细线处方流程轨道。
- 心率线或风险分级轨道，但应低对比、低干扰。
- 数据切片层、证据引用层、审核节点线。
- 首页和登录页可比内部页面更有视觉识别度，但仍要克制。

避免：

- 大幅运动人物海报。
- 健身房暗色照片。
- 霓虹跑道。
- 纯装饰渐变球。
- 玻璃拟态卡片。
- 暗黑电竞风。

## 18. 状态词汇表

风险：

- R0：基础健康维持，可自动生成基础处方。
- R1：低风险改善型，可自动生成改善处方。
- R2：中风险谨慎型，系统可生成初稿但必须专家审核。
- R3：高风险转介型，不生成训练处方。

审核：

- `PENDING_REVIEW`：待专家审核。
- `IN_REVIEW`：审核中。
- `NEEDS_INFO`：待补充资料。
- `APPROVED`：已批准。
- `PUBLISHED`：已发布。
- `REJECTED`：已驳回。
- `REFERRED`：已转介。
- `PAUSED`：已暂停。

动作库：

- `PENDING_REVIEW`：待审核。
- `APPROVED`：已批准。
- `REJECTED`：已驳回。

模板：

- `DRAFT`：草稿。
- `APPROVED`：已批准。
- `ARCHIVED`：已归档。
- `EXPERT_REVIEW_DRAFT`：专家草稿。
- `EXPERT_CONFIRMED`：专家已确认。

知识库：

- `ACTIVE`：已启用。
- `ARCHIVED`：已归档。
- `INDEX_FAILED`：索引失败。
- `SKIPPED`：已跳过。

聚类：

- `TRAINING`：训练中。
- `TRAINED`：已训练。
- `ACTIVE`：已启用。
- `ARCHIVED`：已归档。

科研导出：

- `PENDING`：待审批。
- `APPROVED`：已批准。
- `REJECTED`：已驳回。
- `EXPIRED`：已过期。
- `DOWNLOADED`：已下载。

## 20. 设计禁忌清单

设计 AI 不应做以下事情：

- 不要把系统做成健身 App。
- 不要把首页做成营销页。
- 不要让 R3 页面出现可训练计划。
- 不要让 R2 用户误以为可以直接执行处方。
- 不要只用颜色表示风险。
- 不要隐藏审计和证据链。
- 不要把 AI 生成结果包装成绝对正确。
- 不要把科研数据设计成个体患者列表。
- 不要让导出绕过审批、用途和过期状态。
- 不要用过度动效或装饰背景抢安全状态的注意力。
- 不要大面积玻璃拟态、霓虹、渐变文字、营销口号。
- 不要把复杂页面简化成“几个漂亮卡片”，必须保留任务流和状态机。

## 21. 推荐的重设计验收标准

视觉验收：

- 每个角色首页第一屏能回答该角色当前最重要的问题。
- R0/R1/R2/R3 在全站一致。
- 所有主操作都有明确动词和结果。
- 表格、抽屉、图表、表单、状态徽章风格统一。
- 移动端无横向滚动，按钮可触达。
- 文字不溢出，不遮挡前后内容。

业务验收：

- R3 无训练入口。
- R2 未审核无执行入口。
- 今日运动必须绑定最新已发布处方。
- 专家发布前必须核对安全边界。
- 管理端能看出上线阻断。
- 科研导出能看出脱敏、审批、过期、下载审计。

可访问性验收：

- 正文对比度 >= 4.5:1。
- 图标按钮有可读标签或 tooltip。
- 风险状态不只靠颜色。
- 表单错误靠近字段。
- 关键弹窗可键盘操作。
- 支持减少动效。
